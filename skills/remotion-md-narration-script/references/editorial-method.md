# SeanLab editorial method

Use this reference when drafting or rewriting narration. It distills structural lessons from creator-approved
technology writing samples; it does not authorize copying their wording, hooks, slogans, or personal stories.

## Contents

1. Editorial premise
2. Evidence modules
3. Category routes
4. Spoken-language pass
5. Authored-media pass
6. Final self-review

## Editorial premise

For new projects, the creator's versioned editorial brief is the authority for the premise. Use its motivation,
relationship, audience, takeaway, and category answers before choosing facts from the source inventory. Do not replace
the selected angle with a more generic or easier one. Creator-provided first-person experience may be used as personal
evidence, but external product, event, and procedural claims still need frozen source support.

Before prose, write an internal one-sentence premise that answers:

- Why should this audience care now?
- What single question or judgment will the narration resolve?
- What can the frozen sources actually prove?

Do not output the internal premise as production metadata. Use it to exclude interesting but irrelevant source facts.
The branded opening may remain fixed, but the overview immediately after it must create useful tension through a
concrete problem, change, result, or question. Do not use fake suspense or an unsupported superlative.

## Evidence modules

Organize the middle as two to six natural modules. Each module should perform one main job:

1. State a bounded claim or question.
2. Give a concrete fact, example, test, comparison, or registered source.
3. Explain what that evidence means for the audience.
4. State uncertainty, a failure, or a boundary when relevant.

Evidence comes before judgment. A conclusion must not be stronger than the facts supporting it. Do not turn stars,
downloads, benchmark scores, or a single successful run into popularity, universal superiority, or reliability.
When the source does not make an evaluation, replace adjectives such as mature, complete, reliable, advanced,
professional, or leading with the specific behavior or result the source can prove.

Use specific situations instead of capability labels. Explain a technical noun only when it becomes necessary, then
return to the user's experience. Do not list architecture, dependencies, commands, or internal workflow names unless
the audience needs them to understand or perform the task.

Move between modules because the previous answer creates the next useful question. Avoid mechanical enumeration and
generic transitions. Do not inject a repository-defined transition sentence.

## Category routes

- GitHub project introduction: creator relationship -> real problem -> selected angle -> verified workflow or result ->
  limitation -> bounded recommendation.
- Tutorial: user goal -> prerequisite -> visible action and result pairs -> common failure -> completion check.
- News analysis: event -> verified timeline or facts -> causal explanation -> affected audience -> uncertainty -> view.
- Tool review: real problem -> product position -> representative workflows -> evidence -> limitations -> fit.
- Model review: test question -> comparable evidence -> cost and speed in the same context -> failure case -> bounded
  recommendation. Never equate a benchmark with overall usability.
- Biopharma extra: scientific context -> evidence level -> development implication -> uncertainty -> non-medical
  conclusion.
- Other: choose the closest route, but keep one premise and evidence-led modules.

## Spoken-language pass

Rewrite the structure for speech after the reasoning is sound:

- Prefer short sentences, concrete verbs, and one idea per sentence.
- Mix short emphasis with longer explanations; do not make every sentence the same length.
- Use first-person experience only when the source or creator input supports it.
- Use questions only when the following passage answers them.
- Replace abstract summaries with an example the audience can picture.
- Remove article-only navigation, repeated headings, calls for likes, promotional slogans, and decorative conclusions.
- Add a call to action only when the creator explicitly supplied one in the editorial brief.
- Read every paragraph aloud mentally. Split sentences that require a second breath or contain several relationships.
- Keep precise product names, numbers, units, and uncertainty language intact.
- Screen-led explanation is valid spoken narration: name the interface object, say what the user does, then say what
  changes or why the next step matters. Do not replace a supported walkthrough with an abstract summary.
- Hide the evidence container when it is not the subject. Prefer "打开 Open Design，左侧是输入区域" over "从上传的
  录屏中可以看到输入区域". "我们可以看到 Open Design 的界面" remains valid; the problem is narrating the
  Agent's source-reading process, not describing the interface.
- Remove repetitive report scaffolding such as "值得注意的是", "不难发现", and "综上所述" when a direct sentence
  says the same thing. Do not use a word blacklist when the phrase is necessary to the actual subject.

The narration should sound authored by one person with a reason to speak, not like a neutral catalogue or a product
press release.

## Authored-media pass

Plan media after the spoken argument exists. Follow the creator-confirmed disposition: required uploads must receive one
semantic section binding, while excluded uploads remain absent. Do not distort or repeat the argument merely to create
more asset placements.

Bind or recommend a screenshot when it proves the object, fact, comparison, result, failure, or source being spoken.
Recommend a screen recording for a continuous interaction whose motion or sequence matters. Do not turn every UI step
into a separate screenshot and do not use a personal or decorative image as evidence.

The semantic anchor is the exact spoken sentence that needs the evidence. The downstream workflow determines time.
Never lead a claim by several seconds merely because an asset is already available.

## Final self-review

Before returning JSON, verify:

- The overview makes one clear promise to the audience.
- Every section advances that promise instead of repeating it.
- Every factual judgment is source-backed and proportionate.
- At least one limitation or uncertainty is included when the sources contain one.
- The conclusion answers the opening question and adds no new fact.
- Removing any section would remove a distinct piece of reasoning.
- Spoken text contains no component ids, layout directions, or editing instructions.
- Media recommendations occur at evidence moments and do not force unused candidates into the script.
- A walkthrough still contains its supported interface, action, and result sequence, while uploaded-media references
  remain invisible unless the media itself is the topic.
